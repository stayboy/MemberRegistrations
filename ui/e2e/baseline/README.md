# Live-build screenshot baseline

Generated by `ui/e2e/capture.spec.ts` against the production build, at the viewport of the local mock
each screen is compared with. **Never edit these files by hand**; regenerate them.

```powershell
npm run ui:capture
```

The capture runs on `vite preview` under `/MemberRegistrations/`, with the seeded session and the
stubbed gateway from `ui/e2e/fixtures.ts`, `deviceScaleFactor: 1`, the locale pinned to `en-US`, the
timezone to `UTC`, reduced motion, animations disabled and the caret hidden. It is a separate
Playwright config (`ui/playwright.capture.config.ts`) so `npm run ui:e2e` never writes images.

`member-add` uses the step-flow entry's 1123 px, and `series-detail` its 1000 px because the event detail under the
legacy series path is taller than the fold, rather than a
rounded 900 px, because the form's first step and the series screen are taller than the fold. `imports-batches` has no local
mock; its viewport follows the other 900 px screens.

`member-detail-verified` and `acceptance` were added by the member-verification round (MR-34, MR-51):
the first shows the record header with the badge naming the newest of three proofs on `M-1010`, the
second the public page reached at `v.html#t=<token>` (production serves the same document at `/v`).

The 2026-11-18 capture moved **every** screen, because the `API connected` pill was removed from the
page-title row on all of them (FR-10, owner 2026-11-18). `members-list` and `member-detail` also carry
the `Welfare & Services` label in pixels, and the three `member-detail-overview` rows carry the
rebuilt header and the four cards. A future capture that moves a screen with no member-detail or
list content should be treated as a regression, not drift.

`events-new-period` and `events-new-period-monthly` cover the create form's named-period arm, one
cycle and monthly on Sunday. Because the stub's `POST /events/preview` deliberately resolves no
occurrences (it does not re-implement the resolver), both show the empty preview: the summary reads
`No dates resolve in the next 90 days`, and the one-cycle arm's rail start reads `Resolving the
dates…` because a cycle's start is the resolved first date. That is the fixture's limit, not a
regression; the monthly arm takes its anchor from the rail date and renders it.

`v2-shell/17-find-contact.png` has no capture: the UI ships a `Find by contact` control
(`MembersPage.tsx`), but the capture suite has no case for that dialog yet, although FR-79/AC-48
specify the surface.

Two consecutive runs can differ by roughly 6–30 antialiased border/corner pixels on some cards (usually
under 16); the content and state are stable. There is no pixel gate yet, so this folder is a review
artifact, and any future gate must calibrate against that drift.

The mock folder is git-ignored and local: the durable comparison record lives in the ticket-19 round
doc, not here.
